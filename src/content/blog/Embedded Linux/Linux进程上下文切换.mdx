# Linux 进程上下文切换：CPU 是怎么从 P1 切到 P2 的？

CPU 在某一时刻通常只能真正执行一个进程的指令。如果系统同时有多个可运行进程，操作系统就必须在它们之间不断切换。

这件事就是 **上下文切换（Context Switch）**。

最容易理解的一句话是：

> **切换进程，本质上就是把当前进程的“执行现场”保存起来，再把下一个进程之前保存的“执行现场”恢复到 CPU。**

所谓执行现场，最核心的就是寄存器状态，例如：

\`\`\`text
通用寄存器 R0、R1、R2...
PC  程序计数器
SP  栈指针
FLAGS / 状态寄存器
\`\`\`

其中最关键的是 **PC**。它决定 CPU 下一条应该执行哪条指令。

## 1. 什么叫“进程上下文”？

假设 P1 当前正在执行：

\`\`\`asm
LOAD R0, 12
LOAD R1, 20
ADD  R0, R1
STORE R0, [0x1100]
\`\`\`

执行到第三条之后，CPU 中可能是：

\`\`\`text
R0 = 32
R1 = 20
PC = 0x1003
SP = 0x7FF0
\`\`\`

这几个值描述了：

> “P1 当前执行到哪里，以及执行到这里时 CPU 内部是什么状态。”

这就是进程上下文的一部分。

如果操作系统此时直接把 CPU 给 P2，却不保存这些值，那么以后再回来时，P1 就不知道自己执行到哪里了。

## 2. 上下文保存在哪里？

操作系统会为每个进程维护自己的进程控制信息。

不同系统名字和实现不同，但概念上可以理解成：

\`\`\`text
PCB / task_struct
├─ 进程状态
├─ 调度信息
├─ 内存管理信息
├─ 文件资源
└─ CPU 上下文
   ├─ PC
   ├─ SP
   ├─ 通用寄存器
   └─ 状态寄存器
\`\`\`

Linux 中进程的核心描述结构是 \`task_struct\`。

教学时把“保存的寄存器现场”统称为 PCB 中的一部分比较容易理解，但真实 Linux 内核会把不同类型的上下文分散保存在任务结构、内核栈以及体系结构相关的数据结构中。

因此不要把它理解成：

\`\`\`text
PCB = 一块固定数组，里面简单顺序存 R0、R1、PC、SP
\`\`\`

实际实现会复杂得多。

## 3. 为什么切回来还能继续运行？

答案就在 PC。

假设 P1 切走前：

\`\`\`text
PC = 0x1003
\`\`\`

那么保存现场时，操作系统会记住：

\`\`\`text
P1:
R0 = 32
R1 = 20
PC = 0x1003
SP = 0x7FF0
\`\`\`

之后 P2 使用 CPU：

\`\`\`text
R0 = 100
R1 = 35
PC = 0x2000
\`\`\`

等调度器重新选择 P1 时，再把 P1 的现场装回去：

\`\`\`text
CPU.R0 <- 32
CPU.R1 <- 20
CPU.PC <- 0x1003
CPU.SP <- 0x7FF0
\`\`\`

于是 CPU 下一条继续执行：

\`\`\`asm
STORE R0, [0x1100]
\`\`\`

而不是重新从第一条开始。

所以：

> **进程切换不是重新启动程序，而是“暂停后继续”。**

## 4. 一次上下文切换可以分成几步？

可以把一次 P1 → P2 的切换简化为：

\`\`\`text
① P1 正在运行
      ↓
② 中断 / 时间片结束 / 阻塞 / 调度点
      ↓
③ 进入内核
      ↓
④ 保存 P1 上下文
      ↓
⑤ 调度器选择 P2
      ↓
⑥ 恢复 P2 上下文
      ↓
⑦ 返回用户态
      ↓
⑧ P2 继续运行
\`\`\`

其中调度器做的核心决策是：

\`\`\`text
下一个 CPU 应该给谁？
\`\`\`

而上下文切换做的是：

\`\`\`text
怎么让 CPU 从旧任务的状态，变成新任务的状态？
\`\`\`

这两个概念相关，但不是同一件事。

## 5. 什么情况下会发生上下文切换？

常见情况包括：

\`\`\`text
时间片耗尽
进程主动 sleep
等待 I/O
等待锁
被更高优先级任务抢占
进程退出
中断返回后触发调度
\`\`\`

例如：

\`\`\`c
read(fd, buf, 100);
\`\`\`

如果数据暂时没准备好，当前进程可能进入阻塞状态。

CPU 不会一直傻等，而是：

\`\`\`text
P1 等 I/O
    ↓
P1 BLOCKED
    ↓
调度 P2
    ↓
P2 RUNNING
\`\`\`

## 6. 进程切换为什么有开销？

上下文切换本身并不是“免费”的。

操作系统需要保存和恢复寄存器、运行调度器；不同进程之间切换时还可能涉及地址空间相关状态，并影响 TLB、CPU Cache、分支预测和内存局部性。

所以频繁切换会产生额外开销，这也是为什么不能简单认为“线程或进程开得越多越快”。

## 7. 进程切换和线程切换有什么区别？

同一进程中的线程通常共享代码段、数据段、堆、虚拟地址空间和打开的文件，但每个线程都有自己的 PC、SP、寄存器和线程栈。

因此线程切换同样需要保存和恢复 CPU 上下文。区别是，同一进程内线程切换通常不需要切换完整的进程地址空间，所以一般比不同进程之间切换更轻。

## 8. 和 FreeRTOS 的任务切换有什么关系？

如果已经学过 FreeRTOS，会发现这套思想非常熟悉。

FreeRTOS 的任务切换同样要保存寄存器现场，然后恢复另一个任务的上下文。对于 Cortex-M，PendSV 经常被用于执行任务切换。

从思想上看：

\`\`\`text
Linux 进程调度
FreeRTOS Task 切换
\`\`\`

核心都是：

> **保存当前任务上下文 → 选择下一个任务 → 恢复下一个任务上下文。**

差别主要在系统复杂度、地址空间、权限级别和资源管理方式。

## 9. 一句话记住上下文切换

把整个过程压缩成一条主线：

\`\`\`text
当前进程寄存器
      ↓ 保存
操作系统保存区
      ↓ 调度
另一个进程保存区
      ↓ 恢复
CPU 寄存器
      ↓
继续执行
\`\`\`

所以理解上下文切换时，最值得记住的是这三个动作：

\`\`\`text
Save
  ↓
Schedule
  ↓
Restore
\`\`\`

只要理解了 **PC、SP、寄存器、PCB、调度器** 这几个概念，就能真正理解为什么多个进程看起来像是在“同时运行”。在单核 CPU 上，它们往往只是切换得足够快。
