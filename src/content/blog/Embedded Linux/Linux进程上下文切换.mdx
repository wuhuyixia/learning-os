# Linux 进程上下文切换：CPU 是怎么从 P1 切到 P2 的？

CPU 在某一时刻只能执行当前被调度进程的指令。当系统里有多个可运行进程时，操作系统需要不断在它们之间切换，这就是 **上下文切换（Context Switch）**。

最简单的理解是：

> **先保存当前进程的 CPU 执行现场，再恢复下一个进程之前保存的现场。**

这个“现场”主要包括通用寄存器、程序计数器 PC、栈指针 SP 和状态寄存器等。PC 尤其重要，因为它决定进程恢复后从哪条指令继续。

## 1. 什么叫进程上下文？

假设 P1 正在执行：

```asm
LOAD R0, 12
LOAD R1, 20
ADD  R0, R1
STORE R0, [0x1100]
```

执行到第三条之后，CPU 里可能是：

```text
R0 = 32
R1 = 20
PC = 0x1003
SP = 0x7FF0
```

这些值描述了 P1 当前执行到哪里、寄存器是什么状态。切走之前如果不保存，之后就无法正确恢复。

## 2. 上下文保存在哪里？PCB 又保存什么？

教学上通常会说上下文保存在 PCB 中。Linux 中进程的核心描述结构是 `task_struct`，但真实内核不会简单地把所有寄存器按顺序塞进一个固定数组。

<PCBExplorerDemo />

可以把 PCB 理解成操作系统为每个进程维护的一份“档案”。其中有两类信息：

```text
执行现场：
PC / SP / 通用寄存器 / FLAGS ...

进程资源：
PID / 状态 / 地址空间 / 打开的文件 / I/O 资源 ...
```

真正直接决定“切回来从哪里继续”的，是 PC、SP 和寄存器这类执行上下文；而 PID、文件、I/O、内存信息则帮助操作系统持续管理这个进程。

需要注意的是：**上面的 PCB 是教学模型。** Linux 的实际上下文会分散在 `task_struct`、内核栈和体系结构相关的数据结构中。

## 3. 为什么切回来还能继续？

因为 PC 被保存了。

如果 P1 切走时：

```text
R0 = 32
R1 = 20
PC = 0x1003
SP = 0x7FF0
```

以后恢复 P1 时，操作系统会重新装回这些状态：

```text
CPU.R0 <- 32
CPU.R1 <- 20
CPU.PC <- 0x1003
CPU.SP <- 0x7FF0
```

于是下一条继续执行：

```asm
STORE R0, [0x1100]
```

所以进程切换不是“重启程序”，而是**暂停后继续**。

## 4. 为什么进程切换必须由操作系统来做？

应用程序并不能直接支配 CPU、内存和设备。整个系统可以粗略看成：

```text
Application
    ↓
Operating System
    ↓
CPU / RAM / Disk / I/O
```

普通进程只拥有受限权限。真正负责调度、切换地址空间、管理设备和处理中断的是内核。

因此，进程上下文切换必须由操作系统在内核控制下完成。

## 5. 用户态、内核态与特权指令

CPU 通常会区分普通执行模式和高权限执行模式。不同架构的叫法不同，可以先用下面的抽象理解：

```text
User Mode
  ↓ syscall / interrupt / exception
Kernel / Privileged Mode
  ↓ return
User Mode
```

<PrivilegeModeDemo />

普通应用可以执行 MOV、ADD、PUSH 这类常规指令，但对系统控制、地址空间、设备等敏感操作，必须通过受控入口交给内核处理。

因此系统调用的思想是：

```text
应用需要系统服务
      ↓
执行 syscall
      ↓
CPU 进入内核态
      ↓
操作系统执行受保护操作
      ↓
恢复用户态上下文
      ↓
应用继续运行
```

这也是为什么进程切换经常伴随“进入内核”：调度器本身就是内核的一部分。

## 6. 一次上下文切换的主流程

可以把 P1 → P2 简化成：

```text
P1 RUNNING
    ↓
时钟中断 / 阻塞 / 调度点
    ↓
进入内核
    ↓
保存 P1 上下文
    ↓
调度器选择 P2
    ↓
恢复 P2 上下文
    ↓
P2 RUNNING
```

这里有两个相关但不同的动作：

```text
调度：决定“下一个运行谁”
切换：完成“CPU 状态从旧任务变成新任务”
```

## 7. 什么情况下会触发切换？

常见场景包括：

- 时间片耗尽；
- 进程等待 I/O；
- 进程主动 sleep；
- 等待锁或其他资源；
- 更高优先级任务被唤醒；
- 当前进程退出。

例如：

```c
read(fd, buf, 100);
```

如果数据还没准备好，当前进程可能阻塞。操作系统就可以把 CPU 交给其他就绪进程。

## 8. 为什么上下文切换有开销？

上下文切换不是免费的。系统要保存和恢复寄存器、运行调度逻辑；不同进程切换时还可能切换地址空间相关状态，并影响 TLB、CPU Cache、分支预测和内存局部性。

因此：

> **任务越多不代表一定越快，过于频繁的切换反而会消耗 CPU 时间。**

## 9. 进程切换和线程切换有什么区别？

同一进程中的线程通常共享代码段、数据段、堆、虚拟地址空间和打开的文件，但线程仍各自拥有自己的 PC、SP、寄存器和线程栈。

因此线程切换同样需要保存/恢复 CPU 上下文，只是同一进程内线程切换通常不需要更换完整地址空间，所以一般比不同进程之间切换更轻。

## 10. 和 FreeRTOS 任务切换有什么关系？

如果学过 FreeRTOS，这个过程会很熟悉。

Cortex-M 上的 FreeRTOS 任务切换同样需要保存当前任务寄存器现场，再恢复另一个任务的现场，PendSV 常被用于完成这一步。

核心思想完全一致：

```text
Save
  ↓
Schedule
  ↓
Restore
```

区别主要在于 Linux 还要处理虚拟内存、用户态/内核态、进程资源等更复杂的内容。

## 11. 一句话记住

上下文切换本质就是：

```text
当前进程寄存器
      ↓ 保存
操作系统内核
      ↓ 调度
下一个进程上下文
      ↓ 恢复
CPU 寄存器
      ↓
继续执行
```

只要理解了 **PC、SP、寄存器、PCB、用户态/内核态和调度器**，就能真正理解为什么多个进程在单核 CPU 上看起来像是在“同时运行”。
