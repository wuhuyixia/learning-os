# 在 ISR 中调用 malloc() 一般是不推荐

- malloc() 执行时间不确定。它可能需要遍历空闲链表、合并内存块，耗时不可预测，而 ISR 要求尽量短、确定性强。
- malloc() 通常不是中断安全的。很多 C 库的堆管理内部会使用全局数据结构或锁。如果主线程正在执行 malloc() 时被中断，ISR 又调用一次，可能导致堆结构被破坏，甚至死锁。
- 容易产生内存碎片。嵌入式系统 RAM 很小，频繁动态申请和释放会让堆越来越碎，长期运行可靠性差。
- 可能影响实时性。ISR 中做动态内存管理会延长中断响应时间，影响其他更高优先级任务或中断。

# RISC-V和ARM架构区别

-  ARM 是商业授权架构，指令集和核心设计由 Arm 公司主导，生态非常成熟，广泛应用在手机、MCU、嵌入式和服务器。
- RISC-V 是开放指令集 ISA，本身免费、开放，厂商可以基于标准指令集自行设计 CPU，也可以增加自定义扩展。

# 汇编怎么读寄存器

普通 CPU 寄存器直接通过 MOV/mv 使用；内存映射外设寄存器用 LDR/LW；ARM 系统寄存器通常用 MRS，RISC-V 的 CSR 用 CSRR 系列指令。

# Flash擦写
Flash 不能直接把 0 改回 1，所以本质上都需要先擦后写。“边写边擦”是按 Sector 边擦边写，启动快但写入过程中可能被擦除操作阻塞；“擦完再写”是先把目标区域全部擦除，再连续编程，写入过程更稳定，但前期等待时间更长。

# 内存泄漏

程序申请了一块内存，但后面没有正确释放，而且也失去了这块内存的引用，导致这部分内存一直被占用。
```
内存泄漏：内存被占着，永远没释放
内存碎片：总空闲内存可能不少，但被分成很多小块，无法申请连续的大块内存
```

# Bootloader 中升级和 APP 中升级有什么区别

Bootloader 升级和 APP 升级的主要区别是**升级代码运行的位置和可靠性**。

Bootloader 升级是在独立的 Bootloader 区运行，可以直接擦写 APP，即使 APP 损坏也能重新升级，可靠性更高。

APP 升级是在应用程序中完成下载和校验，一般不会直接覆盖自己，而是设置升级标志后重启，再由 Bootloader 完成固件替换。

简单来说：**APP 负责下载和触发升级，Bootloader 负责真正更新程序和保证升级安全。**

# 高可靠 OTA 怎么保证？每个数据包怎么保证可靠？

高可靠 OTA 我一般分两层保证。

第一层是单包可靠，每个数据包都会带包序号、长度和 CRC。接收端校验通过就回复 ACK，校验失败或者丢包就重传，这样可以保证数据不丢、不乱、不重复。

第二层是整包可靠，固件下载完成以后会再做一次整体 CRC、Hash 或签名校验。

另外为了防止升级过程中掉电，一般会用 A/B 分区或者备份区，新固件验证成功以后再切换。如果新版本启动失败，还可以自动回滚到旧版本。

简单来说就是：**单包靠序号、CRC 和重传，整包靠完整性校验，系统层面靠 A/B 和回滚防止变砖。**

# I2C 采集任务优先级怎么设计？多任务怎么保护临界资源？

I2C 采集任务的优先级，我一般根据**采样周期和实时性要求**来定。

如果这个传感器数据是控制环或者保护逻辑要用的，我会把采集任务优先级设高一些；如果只是温度、电量这类慢速数据，优先级可以低一些。一般不会把 I2C 任务设成系统最高优先级，避免 I2C 通信时间比较长，把其他关键任务堵住。

多任务访问临界资源时，比如多个任务共用同一个 I2C 总线，我会加 **Mutex 互斥锁**，谁拿到锁谁访问 I2C，用完立即释放。

如果是很短的共享变量操作，可以用临界区或者关中断保护；如果是任务间同步，可以用信号量、事件或者消息队列。

另外用 Mutex 的话，最好支持**优先级继承**，避免出现优先级反转。

简单来说就是：**任务优先级按实时性来排，共享 I2C 用 Mutex，短临界资源用临界区，任务同步用信号量或队列。**

# 优先级继承后任务怎么调度？什么时候触发任务调度？

优先级继承主要是解决**优先级反转**。

比如低优先级任务 L 拿着 Mutex，高优先级任务 H 也来申请这个 Mutex，这时候 H 会被阻塞。RTOS 会临时把 L 的优先级提升到 H 的优先级，让 L 尽快把临界区执行完并释放 Mutex。

Mutex 释放以后，L 的优先级会恢复到原来的优先级，然后 H 变成就绪态。如果 H 的优先级比当前任务高，就会马上触发任务切换，开始执行 H。

任务调度一般会在这几种情况下触发：**高优先级任务进入就绪态、当前任务阻塞或延时、释放信号量或 Mutex 唤醒了高优先级任务、时间片到期，以及中断退出时发现有更高优先级任务就绪。**

简单来说就是：**优先级继承让低优先级任务临时“提速”释放资源，资源释放后再恢复优先级，并调度当前最高优先级的就绪任务。**

```
TickType_t start = xTaskGetTickCount();

func();

TickType_t end = xTaskGetTickCount();

耗时 = (end-start) × portTICK_PERIOD_MS
```

```
uint32_t start = DWT->CYCCNT;

func();

uint32_t cycles = DWT->CYCCNT - start;

time = cycles / CPU主频
```

# RTOS 中断怎么保护共享资源？中断修改全局变量有问题吗？

RTOS 里如果中断和任务会同时访问同一个共享资源，我一般会根据资源类型做保护。

如果只是很短的共享变量操作，可以在任务侧进入临界区或者短时间关中断，避免任务访问过程中被中断打断。

中断里一般不能直接用普通 Mutex，因为 Mutex 可能导致阻塞，中断上下文不能睡眠。通常要用 RTOS 提供的 ISR 接口，比如 FromISR 的信号量、队列或者事件通知，把数据通知给任务处理。

中断修改全局变量本身不是一定有问题，关键看它是不是被任务同时访问。如果同时读写，就可能出现竞争条件。除了加 volatile 保证每次都从内存访问之外，还要考虑原子性和同步问题，volatile 本身并不能保证线程安全。

简单来说就是：**中断里尽量少做事，共享数据要做临界区或原子保护，复杂处理通过队列、信号量通知任务来完成。**

# 什么时候会发生页表错误 / Page Fault

Page Fault 本质上就是 CPU 访问某个虚拟地址时，MMU 查页表发现这个地址当前不能正常完成访问，于是触发异常。

常见情况有几种：第一种是这个虚拟页还没有映射到物理内存，比如按需分页，第一次访问时会触发 Page Fault，操作系统再把页面加载进来。

第二种是页面被换出到磁盘了，访问时需要重新换入内存。

第三种是权限不对，比如只读页被写、用户态访问内核地址，或者访问了不可执行页面。

还有一种就是访问非法地址，比如空指针、野指针或者已经释放的内存，这种 Page Fault 通常无法恢复，最后可能导致进程崩溃。

简单来说就是：**地址没映射、页面不在内存、访问权限错误或者地址非法，都可能触发 Page Fault。**


# 为什么使用 IDLE 中断，而不用普通接收中断？

如果是 UART 接收，我用 IDLE 中断主要是为了处理**不定长数据**。

普通接收中断一般是每收到一个字节就进一次中断，数据量大的时候中断会很频繁，CPU 开销比较大。

IDLE 中断可以配合 DMA 使用，DMA 负责连续接收数据，当串口一段时间没有新数据、出现空闲帧时，再触发一次 IDLE 中断。这时候根据 DMA 剩余计数就能算出实际收到多少字节。

这样做的优点就是：**中断次数少、CPU 占用低，而且很适合不定长协议。**

简单来说就是：**普通接收中断偏逐字节处理，IDLE + DMA 更适合高吞吐、不定长数据接收。**
