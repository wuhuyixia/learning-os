# MISRA-C 规范

在普通 C 项目中，只要代码能够编译、运行结果看起来正确，很多写法都可能被接受。但在汽车电子、工业控制、机器人底层控制、医疗设备等场景中，软件不仅要求“能运行”，还要求：

- 行为可以预测；
- 代码能够审查；
- 平台切换后行为不应突然变化；
- 边界条件和异常路径必须明确；
- 尽量在编译期或静态分析阶段发现风险。

MISRA-C 的核心价值就在这里：**主动限制 C 语言中过于灵活、容易产生歧义或未定义行为的部分。**

它并不是一种新的编程语言，也不是要求把所有代码写成某一种固定形式，而是通过一组规则和指令，让 C 代码更加适合高可靠嵌入式系统。

## 1. 为什么嵌入式系统特别需要 MISRA-C

C 语言非常接近硬件，因此非常适合 MCU、驱动、RTOS、Bootloader 和底层控制程序。但这种灵活性也带来了风险。

例如下面的代码：

```c
uint8_t speed = 250U;
int8_t delta = -20;

speed = speed + delta;
```

从阅读习惯上看，我们很容易理解成：

```text
250 + (-20) = 230
```

但真正执行时，还会涉及：

- 整数提升；
- signed / unsigned 转换；
- 中间表达式的类型；
- 最终赋值时的收窄转换。

也就是说，一段“看起来简单”的代码，实际语义可能依赖 C 标准中的整数转换规则。

MISRA-C 的思路不是让程序员记住所有隐式规则，而是要求代码把这些意图写得更明确。

例如：

```c
uint8_t speed = 250U;
int8_t delta = -20;

int16_t next = (int16_t)speed + (int16_t)delta;

if ((next >= 0) && (next <= UINT8_MAX))
{
    speed = (uint8_t)next;
}
```

这段代码虽然更长，但有两个优点：

1. 中间运算范围明确；
2. 收窄转换前进行了边界检查。

这也是 MISRA-C 很重要的一种思想：

> **代码首先写给人审查，其次才是写给编译器执行。**

# 2. MISRA-C 中最重要的几个概念

MISRA-C 的要求通常可以分成不同层次。学习时不需要一开始就背完整规则编号，更重要的是理解下面几个概念。

## 2.1 Directive 与 Rule

可以粗略理解为：

```text
Directive
    ↓
偏向开发过程、设计、工具、文档层面的要求

Rule
    ↓
可以直接作用于 C 源码写法的规则
```

例如：

- 是否应该对某类异常进行记录；
- 是否应限制某种语言结构；
- 某种表达式是否允许出现；
- 指针转换是否合法；
- 控制流是否足够明确。

在实际工程里，MISRA-C 通常会和静态分析工具配合使用。

```text
源代码
  ↓
编译器警告
  ↓
MISRA 静态分析
  ↓
人工 Code Review
  ↓
单元测试 / 集成测试
```

没有任何一层可以完全替代其它层。

---

## 2.2 Mandatory、Required、Advisory

不同规则的重要程度不同。

可以这样理解：

| 类型 | 理解方式 |
| :--- | :--- |
| Mandatory | 必须满足，不能随意偏离 |
| Required | 原则上必须满足，特殊情况下需要正式记录偏离理由 |
| Advisory | 推荐遵守，可以根据项目约束进行判断 |

因此 MISRA 项目并不意味着“看到告警就全部机械修改”，而是要建立**可追踪的合规流程**。

# 3. 类型系统：MISRA-C 最核心的部分之一

在嵌入式程序中，很多问题并不是算法错误，而是类型问题。

常见风险包括：

```text
signed ↔ unsigned
宽类型 ↔ 窄类型
整数 ↔ 浮点
枚举 ↔ 整数
指针 ↔ 整数
```

## 3.1 尽量使用明确宽度的整数类型

嵌入式项目中通常更推荐：

```c
#include <stdint.h>

uint8_t
int8_t
uint16_t
int16_t
uint32_t
int32_t
```

而不是在通信协议和寄存器处理中大量依赖：

```c
char
short
int
long
```

原因是不同编译器和不同架构中，基本类型宽度可能不同。

例如通信帧：

```c
typedef struct
{
    uint8_t id;
    uint16_t voltage_mv;
    int16_t current_ma;
} BatteryFrame;
```

比下面这种表达更明确：

```c
typedef struct
{
    unsigned char id;
    unsigned int voltage;
    int current;
} BatteryFrame;
```

尤其在 CAN、UART、SPI、Flash 数据格式中，类型宽度必须和协议定义严格对应。

---

## 3.2 不要依赖隐式收窄

风险写法：

```c
uint32_t adc_raw = 70000U;
uint16_t adc = adc_raw;
```

`uint16_t` 无法表示 70000，因此结果会发生截断。

更容易审查的方式是：

```c
uint32_t adc_raw = 70000U;
uint16_t adc = 0U;

if (adc_raw <= UINT16_MAX)
{
    adc = (uint16_t)adc_raw;
}
```

显式转换并不能自动让代码安全。

```c
adc = (uint16_t)adc_raw;
```

只能说明“程序员明确要求做这个转换”，但**并不能证明数值一定没有溢出**。

所以真正安全的流程应该是：

```text
确认范围
   ↓
再转换
   ↓
再使用
```

---

## 3.3 signed 与 unsigned 不要随意混合

例如：

```c
uint16_t count = 0U;
int16_t offset = -1;

if (count + offset > 10)
{
    /* ... */
}
```

这种代码的问题不是一定错误，而是**读代码的人必须先推导表达式最终类型**。

更加明确的做法是：

```c
int32_t result = (int32_t)count + (int32_t)offset;

if (result > 10)
{
    /* ... */
}
```

# 4. 常量也应该表达类型意图

很多嵌入式代码会写：

```c
uint32_t timeout = 1000;
```

更加明确的写法是：

```c
uint32_t timeout = 1000U;
```

例如：

```c
if (counter >= 100U)
{
    counter = 0U;
}
```

`U` 明确说明这是 unsigned 常量。

对于长整型也可以使用：

```c
1000UL
```

这种写法的意义不在于“格式统一”，而在于**减少表达式中无意发生的 signed / unsigned 类型混合**。

# 5. 指针必须让有效性更清晰

裸指针本身只能告诉我们一个地址，却不能告诉我们：

- 是否允许为空；
- 指向的对象是否仍然有效；
- 谁拥有这个对象；
- 是否允许修改；
- 数组长度是多少。

因此 MISRA-C 对指针相关写法非常谨慎。

## 5.1 解引用之前检查必要条件

风险代码：

```c
uint32_t *p = get_data();
*p = 100U;
```

更明确：

```c
uint32_t *p = get_data();

if (p != NULL)
{
    *p = 100U;
}
```

这里并不是说每个指针都必须机械检查 NULL。

如果函数接口已经通过设计保证返回值必定非空，那么更重要的是：**这个前置条件必须在接口层面明确并可验证。**

---

## 5.2 const 可以表达“只读意图”

例如：

```c
void send_frame(const uint8_t *data, uint16_t len);
```

相比：

```c
void send_frame(uint8_t *data, uint16_t len);
```

第一种接口能够直接告诉调用者：

> `send_frame()` 不应该修改传入缓冲区。

这会明显降低大型项目中的接口理解成本。

---

# 6. 数组：边界比语法更重要

嵌入式系统中数组越界往往直接意味着：

```text
覆盖栈
覆盖任务控制块
覆盖状态变量
覆盖通信缓冲区
程序异常复位
```

例如：

```c
uint8_t data[8];

for (uint8_t i = 0U; i <= 8U; i++)
{
    data[i] = 0U;
}
```

这里 `i == 8` 时已经越界。

正确写法：

```c
for (uint8_t i = 0U; i < 8U; i++)
{
    data[i] = 0U;
}
```

更推荐把长度和数组联系起来：

```c
#define DATA_LEN (8U)

uint8_t data[DATA_LEN];

for (uint8_t i = 0U; i < DATA_LEN; i++)
{
    data[i] = 0U;
}
```

这样数组尺寸修改后，循环边界不会被遗漏。

# 7. switch：控制流必须让人一眼看懂

下面是非常典型的风险代码：

```c
switch (state)
{
case 0:
    motor_start();

case 1:
    motor_run();
    break;
}
```

当 `state == 0` 时，程序会继续执行 `case 1`。

这种 fall-through 有时是故意的，但如果不是非常明确，就容易变成缺陷。

更加稳妥的方式：

```c
switch (state)
{
case MOTOR_IDLE:
    motor_start();
    break;

case MOTOR_RUNNING:
    motor_run();
    break;

case MOTOR_ERROR:
    motor_stop();
    break;

 default:
    motor_enter_safe_state();
    break;
}
```

这里还有一个重要思想：

```text
正常状态 → 明确处理
未知状态 → 进入安全路径
```

对于电机、BMS、充电器、工业控制器等系统，这一点尤其重要。

---

# 8. if / else 也应该让控制流完整

例如：

```c
if (temperature > 80)
    fan_on();
```

虽然语法完全合法，但在安全编码中更推荐明确使用大括号：

```c
if (temperature > 80)
{
    fan_on();
}
```

原因是后续维护时非常容易变成：

```c
if (temperature > 80)
    fan_on();
    alarm_on();
```

此时 `alarm_on()` 实际不属于 `if`。

显式大括号可以避免这类维护性错误。

---

# 9. 宏：少一点“聪明”，多一点确定性

C 预处理器非常强大，但它执行的是**文本替换**，不是普通函数调用。

例如：

```c
#define MAX(a, b) ((a) > (b) ? (a) : (b))

int y = MAX(i++, 10);
```

展开后可能导致 `i++` 被执行多次。

因此对于有类型和行为的逻辑，更推荐函数：

```c
static int32_t max_i32(int32_t a, int32_t b)
{
    return (a > b) ? a : b;
}
```

调用：

```c
int32_t y = max_i32(i, 10);
i++;
```

这样：

- 参数只求值一次；
- 类型明确；
- 可以单步调试；
- 静态分析更容易理解。

---

## 9.1 宏参数一定要注意括号

风险写法：

```c
#define SQUARE(x) x * x
```

调用：

```c
int y = SQUARE(a + b);
```

展开后：

```c
int y = a + b * a + b;
```

显然不是预期结果。

至少应该写成：

```c
#define SQUARE(x) ((x) * (x))
```

但如果 `x` 含副作用：

```c
SQUARE(i++)
```

问题仍然存在。

因此对于复杂逻辑：

> **优先函数，宏只做简单、无副作用、意图明确的替换。**

---

# 10. 表达式不要隐藏副作用

例如：

```c
array[i++] = i;
```

阅读者需要同时判断：

- `i++` 什么时候发生；
- 右侧 `i` 读取的是哪个值；
- 表达式求值顺序是否存在依赖。

更加稳妥：

```c
array[i] = i;
i++;
```

安全编码很强调：

```text
一个语句
↓
尽量只表达一个核心动作
```

尤其在状态机和中断服务程序里，这能明显降低审查难度。

# 11. 动态内存为什么在嵌入式安全项目中很敏感

在 PC 程序里：

```c
malloc()
free()
```

十分常见。

但在长时间运行的 MCU 或实时系统里，动态分配可能带来：

- 内存碎片；
- 分配失败；
- 执行时间不确定；
- 生命周期难追踪；
- double free；
- use-after-free。

例如：

```c
uint8_t *buf = malloc(size);
```

运行 1 次可能没有问题，但系统运行几个月以后，可用堆空间可能已经高度碎片化。

对于固定最大容量的缓冲区，更容易预测的方式通常是：

```c
#define RX_BUFFER_SIZE (256U)

static uint8_t rx_buffer[RX_BUFFER_SIZE];
```

这种方式在编译期就已经确定了 RAM 上界。

---

## 11.1 静态分配并不等于“浪费内存”

安全系统更关心的是：

```text
最大占用是多少？
什么时候申请？
什么时候释放？
最坏情况下是否还能运行？
```

而不是只关注平均内存利用率。

例如 FreeRTOS 项目中，很多高可靠系统也会选择：

```text
静态任务
静态队列
静态信号量
静态内存池
```

来换取更加确定的运行时行为。

---

# 12. 标准库函数也不能“拿来就用”

不是所有标准 C 库函数都适合直接进入安全关键代码。

例如：

```c
strcpy(dst, src);
```

如果 `src` 长度超过 `dst`，就可能越界。

更安全的思路是：

```c
if (src_len < sizeof(dst))
{
    memcpy(dst, src, src_len);
    dst[src_len] = '\0';
}
```

重点仍然是：

```text
长度从哪里来？
目标容量是多少？
边界是否检查？
```

而不是简单认为“换一个函数名就安全”。

---

# 13. volatile 不是线程同步工具

在嵌入式里经常看到：

```c
volatile uint8_t flag;
```

`volatile` 的主要作用是告诉编译器：

> 这个对象的值可能在程序看不到的位置发生变化，因此每次访问都应真正进行读写。

典型场景包括：

- 硬件寄存器；
- ISR 与主程序共享的简单状态；
- 某些特殊内存映射区域。

但是：

```text
volatile ≠ 原子操作
volatile ≠ mutex
volatile ≠ memory barrier
volatile ≠ 线程安全
```

例如：

```c
volatile uint32_t counter;

counter++;
```

仍然可能不是原子操作。

如果变量跨任务或跨核访问，还需要考虑 RTOS 临界区、原子操作或锁机制。

---

# 14. 位运算必须特别关注类型和位宽

寄存器代码常见：

```c
reg |= (1 << 31);
```

更加明确：

```c
reg |= (1UL << 31U);
```

原因是 `1` 默认是有符号 `int`，左移到高位时可能引入不必要的平台依赖和风险。

对于寄存器定义，推荐：

```c
#define UART_CR1_TXEIE (1UL << 7U)
```

这样位宽和 unsigned 意图更加清楚。

---

# 15. 枚举比“魔法数字”更容易审查

风险写法：

```c
if (motor_state == 3)
{
    motor_stop();
}
```

读代码的人并不知道 `3` 是什么。

推荐：

```c
typedef enum
{
    MOTOR_IDLE = 0,
    MOTOR_STARTING,
    MOTOR_RUNNING,
    MOTOR_ERROR
} MotorState;
```

使用：

```c
if (motor_state == MOTOR_ERROR)
{
    motor_stop();
}
```

这种写法使控制逻辑本身变成了文档。

---

# 16. 函数要尽量让输入、输出和副作用清楚

例如：

```c
void update(void);
```

这个函数名很难看出它会修改什么。

如果函数内部同时：

```text
读取 ADC
更新全局变量
发送 CAN
写 Flash
修改状态机
```

那么它会非常难测试。

更加合理的是拆成：

```c
static uint16_t read_voltage_mv(void);
static MotorState update_motor_state(uint16_t voltage_mv);
static void send_motor_status(MotorState state);
```

这种设计和 MISRA 的思想是一致的：

> **减少隐藏依赖，让数据流和控制流更容易分析。**

---

# 17. 全局变量不是不能用，而是要受控

嵌入式程序几乎不可能完全没有全局状态。

真正的问题是：

```text
谁可以修改？
什么时候修改？
是否跨中断？
是否跨任务？
是否存在并发访问？
```

例如：

```c
uint32_t g_speed;
```

如果整个工程几十个文件都能修改它，调试会非常困难。

更合理的方式是把变量封装在模块内部：

```c
static uint32_t motor_speed;
```

并通过接口访问：

```c
uint32_t Motor_GetSpeed(void);
void Motor_SetTargetSpeed(uint32_t speed);
```

这样模块边界更加清晰。

---

# 18. 递归为什么通常不适合资源受限系统

递归：

```c
void func(uint32_t n)
{
    if (n > 0U)
    {
        func(n - 1U);
    }
}
```

每次调用都会创建新的栈帧。

如果递归深度难以严格界定，就很难回答：

```text
最坏情况下需要多少栈？
```

因此在嵌入式实时系统中，更倾向于使用有明确上界的循环：

```c
while (n > 0U)
{
    n--;
}
```

这样资源使用更加可预测。

---

# 19. assert 与运行时错误处理不是一回事

开发阶段可以写：

```c
assert(ptr != NULL);
```

但安全关键系统不能简单依赖 `assert()` 作为唯一错误处理机制。

例如生产环境可能关闭断言。

真正需要考虑的是：

```text
错误发生后
  ↓
能否继续运行？
  ↓
是否进入 safe state？
  ↓
是否记录故障？
  ↓
是否需要复位？
```

例如：

```c
if (sensor == NULL)
{
    fault_set(FAULT_SENSOR_POINTER);
    system_enter_safe_state();
}
```

# 20. MISRA 偏离（Deviation）不是“忽略告警”

实际项目中，有些规则可能由于底层硬件、编译器接口或第三方代码无法完全满足。

例如硬件寄存器地址转换：

```c
#define GPIOA ((GPIO_TypeDef *)0x40020000UL)
```

从纯语言层面看，整数与指针之间的转换非常敏感，但 MCU 寄存器映射又确实需要这种机制。

这类情况不应该简单写：

```text
ignore warning
```

更合理的是建立正式 deviation 记录：

```text
规则
↓
为什么无法满足
↓
适用代码范围
↓
风险是什么
↓
为什么风险可接受
↓
采取了哪些补偿措施
↓
谁批准
```

这就是工程上的“受控偏离”。

# 21. 静态分析工具在 MISRA 开发中的位置

大型项目不可能完全依赖人工检查 MISRA。

通常流程类似：

```text
开发者写代码
      ↓
Compiler Warning
      ↓
Static Analyzer
      ↓
MISRA Rule Check
      ↓
Code Review
      ↓
Unit Test
      ↓
CI Gate
```

常见检查项目包括：

- 未初始化变量；
- 不可达代码；
- 空指针风险；
- 数组越界；
- 隐式类型转换；
- signed / unsigned 混用；
- switch 分支；
- 宏副作用；
- 指针类型转换；
- 规则偏离。

因此 MISRA-C 并不是“写完代码最后跑一次工具”，而应该融入整个开发流程。

# 22. 一个更接近嵌入式项目的例子

下面是一段简单的电池电压检查代码。

风险版本：

```c
int voltage;
char error;

void check(void)
{
    voltage = ADC_Read();

    if (voltage > 4200)
        error = 1;
}
```

这里存在多个工程问题：

- `int` 位宽意图不明确；
- `char` 是否 signed 依赖实现；
- 全局变量可以被其它模块直接修改；
- `if` 没有大括号；
- `4200` 的类型意图不明确；
- 状态只有 `1`，错误语义不明确。

更加工程化的版本：

```c
#include <stdint.h>
#include <stdbool.h>

#define BATTERY_OVERVOLTAGE_MV (4200U)

static uint16_t battery_voltage_mv = 0U;
static bool battery_overvoltage = false;

static void Battery_UpdateProtection(void)
{
    battery_voltage_mv = ADC_ReadVoltageMv();

    if (battery_voltage_mv > BATTERY_OVERVOLTAGE_MV)
    {
        battery_overvoltage = true;
    }
    else
    {
        battery_overvoltage = false;
    }
}
```

这段代码不一定代表所有项目中的唯一正确写法，但它具备 MISRA 风格安全代码的一些典型特点：

```text
类型明确
常量明确
作用域受控
控制流明确
变量语义明确
```

# 23. 在 STM32 / FreeRTOS 项目中怎么实际使用

如果你正在做 STM32 项目，不需要一开始就把整个工程一次性改成严格 MISRA 合规。

可以先从最有收益的几项开始。

## 第一阶段：编译器警告

例如 GCC：

```bash
-Wall
-Wextra
-Wconversion
-Wsign-conversion
-Wshadow
```

先把普通编译告警清理干净。

## 第二阶段：统一基础类型

项目里逐步采用：

```c
uint8_t
uint16_t
uint32_t
int8_t
int16_t
int32_t
bool
```

## 第三阶段：清理高风险写法

优先处理：

```text
数组越界
NULL 解引用
隐式收窄
signed / unsigned 混用
宏副作用
switch fall-through
动态内存
复杂全局状态
```

## 第四阶段：接入静态分析

将检查加入 CI：

```text
push code
   ↓
build
   ↓
static analysis
   ↓
MISRA check
   ↓
unit test
```

这样规范就不会只停留在文档里。

# 24. 面试中如何解释 MISRA-C

如果面试官问：

> MISRA-C 是什么？

可以回答：

> MISRA-C 是面向高可靠和安全关键嵌入式系统的一套 C 语言安全编码规范。它通过限制 C 中容易引发未定义行为、隐式类型转换、复杂控制流、危险指针和动态内存等写法，提高代码的可预测性、可移植性和可审查性。实际项目中通常会结合编译器告警、静态分析、Code Review 和 deviation 管理一起使用。

如果继续问：

> 为什么普通 C 能运行还需要 MISRA？

可以回答：

> 因为“当前编译器上能运行”不等于“所有边界条件和目标平台上行为都确定”。MISRA 更关注最坏情况、未定义行为、平台差异和长期维护风险。

如果继续问：

> MISRA-C 最常见的检查点有哪些？

可以答：

```text
整数类型和隐式转换
signed / unsigned 混合
数组边界
指针有效性
switch 控制流
宏副作用
动态内存
全局变量作用域
库函数安全使用
规则偏离管理
```

真正理解 MISRA-C 的关键，不是背下规则编号，而是形成一种习惯：

> **看到一段代码时，不只问“能不能运行”，还要问“它的行为是否明确、边界是否可证明、最坏情况是否可接受、别人能不能快速审查出来”。**
