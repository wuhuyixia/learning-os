# 嵌入式串口通信：自定义协议设计

UART 只提供字节传输能力，不提供消息边界、命令语义、完整性校验和应答机制。因此工程中通常需要在 UART 之上定义应用层协议。

![串口协议设计总览](/learning-os/images/uart-protocol-handdrawn.svg)

## 1. 简化版帧格式

一个基础协议可以定义为：

| 字段 | 长度 | 说明 |
| --- | ---: | --- |
| SOF | 1~2 B | 帧头 |
| CMD | 1 B | 命令码 |
| LEN | 1~2 B | DATA 长度 |
| DATA | 0~N B | 有效负载 |
| CHECK | 1 B | 校验值 |
| EOF | 1~2 B | 帧尾，可选 |

示例：

```text
55 02 02 0A 0B 19 EE
```

对应：

```text
SOF   = 0x55
CMD   = 0x02
LEN   = 0x02
DATA  = 0x0A 0x0B
CHECK = 0x19
EOF   = 0xEE
```

其中：

```text
CHECK = CMD + LEN + DATA[0] + DATA[1]
      = 0x02 + 0x02 + 0x0A + 0x0B
      = 0x19
```

## 2. 帧头设计

常见帧头有：

```text
0x55
0xAA
0x55AA
0xAA55
```

`0x55 = 01010101`，`0xAA = 10101010`，比特翻转明显，便于逻辑分析仪观察。

帧头只用于辅助同步，不能单独承担帧边界判断。稳定的接收逻辑应同时使用：

```text
SOF + LEN + 超时 + 校验 + 状态机
```

## 3. CMD 与 LEN

### CMD

CMD 用于定义业务功能，例如：

| CMD | 功能 |
| --- | --- |
| `0x01` | 读取参数 |
| `0x02` | 设置参数 |
| `0x03` | 读取状态 |
| `0x04` | 设备复位 |

接收端解析后按命令分发：

```c
switch (frame.cmd)
{
    case 0x01:
        read_parameter();
        break;

    case 0x02:
        set_parameter(frame.data, frame.len);
        break;

    case 0x03:
        send_status();
        break;

    default:
        send_error();
        break;
}
```

### LEN

LEN 表示负载长度，主要用于处理变长帧、分包和粘包。

例如：

```text
LEN = 3
DATA = 11 22 33
```

接收端只有在收到 3 Byte DATA 后，才进入校验阶段。

## 4. 字节序

多字节字段必须规定传输顺序。

以 `0x12345678` 为例：

| 字节序 | 传输顺序 |
| --- | --- |
| Little Endian | `78 56 34 12` |
| Big Endian | `12 34 56 78` |

协议应显式规定以下字段的字节序：

- LEN；
- SEQ；
- CRC；
- 16/32 位参数；
- 时间戳。

不要直接依赖 MCU 内部存储格式。

例如按大端编码 16 位整数：

```c
static void put_u16_be(uint8_t *buf, uint16_t value)
{
    buf[0] = (uint8_t)(value >> 8);
    buf[1] = (uint8_t)(value & 0xFF);
}

static uint16_t get_u16_be(const uint8_t *buf)
{
    return ((uint16_t)buf[0] << 8) | buf[1];
}
```

## 5. 校验设计

### 累加和

实现简单：

```c
static uint8_t checksum8(const uint8_t *buf, uint16_t len)
{
    uint8_t sum = 0;

    for (uint16_t i = 0; i < len; ++i)
    {
        sum += buf[i];
    }

    return sum;
}
```

### CRC

工程协议通常使用 CRC8 或 CRC16。

| 校验方式 | 特点 | 适用场景 |
| --- | --- | --- |
| 累加和 | 实现简单，检错能力较弱 | 简单控制帧 |
| CRC8 | 开销小，检错能力较好 | 短帧 |
| CRC16 | 检错能力更强 | 工程通信 |

CRC 两端必须统一：

```text
Polynomial
Init
RefIn
RefOut
XorOut
字节序
校验覆盖范围
```

## 6. 工程版帧格式

复杂系统建议增加版本、地址、序号和标志位：

| 字段 | 长度 | 作用 |
| --- | ---: | --- |
| SOF | 1~2 B | 帧同步 |
| VER | 1 B | 协议版本 |
| FLAGS | 1 B | 控制标志 |
| SRC | 1~2 B | 源地址 |
| DST | 1~2 B | 目的地址 |
| SEQ | 1~2 B | 帧序号 |
| CMD | 1 B | 命令码 |
| LEN | 1~2 B | PAYLOAD 长度 |
| PAYLOAD | 0~N B | 业务数据 |
| CRC16 | 2 B | 完整性校验 |
| EOF | 1 B | 可选帧尾 |

工程版的核心目的不是增加字段，而是支持：

```text
版本兼容
多节点
请求/响应
错误返回
重复包检测
超时重传
可靠校验
```

## 7. FLAGS

FLAGS 可以按 bit 定义：

| Bit | 名称 | 含义 |
| --- | --- | --- |
| bit0 | ACK_REQ | 需要应答 |
| bit1 | RESPONSE | 响应帧 |
| bit2 | ERROR | 错误帧 |
| bit3 | EVENT | 主动上报 |
| bit4~7 | Reserved | 保留 |

例如：

```text
CMD = SET_PARAM
FLAGS.ACK_REQ = 1
```

表示该命令执行后必须返回响应。

## 8. SEQ、ACK 与重传

SEQ 用于请求和响应配对，也可用于重复帧检测。

请求：

```text
SEQ = 0x25
CMD = SET_PARAM
```

响应：

```text
SEQ = 0x25
FLAGS.RESPONSE = 1
```

推荐流程：

```text
发送请求
   ↓
启动超时计时
   ↓
收到相同 SEQ 的 ACK/Response
   ├─ 是：完成
   └─ 否：超时后重传
             ↓
        超过最大次数
             ↓
        通信故障
```

重传必须配合 SEQ 去重，否则写 Flash、控制电机、开关阀门等命令可能被重复执行。

## 9. SRC 与 DST

当系统从点对点扩展到多设备时，SRC/DST 用于节点寻址。

例如：

```text
0x01  主控
0x10  BMS
0x11  电机控制器
0x12  显示屏
0xFF  广播
```

收到数据后先检查：

```text
DST == 本机地址
或
DST == 广播地址
```

否则直接丢弃。

## 10. 接收状态机

UART 数据可能出现：

```text
分包
粘包
残帧
错误字节
超时
缓冲区溢出
```

因此接收端不应依赖一次中断就获得完整帧，而应按状态逐步解析：

```text
WAIT_SOF
   ↓
READ_HEADER
   ↓
READ_PAYLOAD
   ↓
READ_CRC
   ↓
CHECK_FRAME
   ↓
DISPATCH
```

异常时恢复到 `WAIT_SOF`，重新寻找下一帧。

## 11. 简化版接收状态机

```c
typedef enum
{
    RX_WAIT_SOF = 0,
    RX_CMD,
    RX_LEN,
    RX_DATA,
    RX_CHECK,
    RX_EOF
} RxState;

typedef struct
{
    RxState state;
    uint8_t cmd;
    uint8_t len;
    uint8_t data[64];
    uint8_t index;
    uint8_t check;
} ProtoRx;

void proto_rx_byte(ProtoRx *rx, uint8_t byte)
{
    switch (rx->state)
    {
        case RX_WAIT_SOF:
            if (byte == 0x55)
            {
                rx->index = 0;
                rx->state = RX_CMD;
            }
            break;

        case RX_CMD:
            rx->cmd = byte;
            rx->state = RX_LEN;
            break;

        case RX_LEN:
            if (byte > sizeof(rx->data))
            {
                rx->state = RX_WAIT_SOF;
                break;
            }

            rx->len = byte;
            rx->index = 0;
            rx->state = (rx->len == 0) ? RX_CHECK : RX_DATA;
            break;

        case RX_DATA:
            rx->data[rx->index++] = byte;

            if (rx->index >= rx->len)
            {
                rx->state = RX_CHECK;
            }
            break;

        case RX_CHECK:
            rx->check = byte;
            rx->state = RX_EOF;
            break;

        case RX_EOF:
            if (byte == 0xEE &&
                rx->check == checksum8_frame(rx->cmd,
                                             rx->len,
                                             rx->data))
            {
                protocol_dispatch(rx->cmd,
                                  rx->data,
                                  rx->len);
            }

            rx->state = RX_WAIT_SOF;
            break;

        default:
            rx->state = RX_WAIT_SOF;
            break;
    }
}
```

实际工程中还应增加：

- 帧接收超时；
- CRC16；
- DMA；
- RingBuffer；
- 错误码；
- ACK；
- SEQ；
- 最大帧长保护。

## 12. 发送封包

```c
#define SOF             0x55
#define EOF_BYTE        0xEE
#define MAX_DATA_LEN    64

size_t protocol_pack(uint8_t cmd,
                     const uint8_t *data,
                     uint8_t len,
                     uint8_t *out,
                     size_t out_size)
{
    size_t frame_len = 1U + 1U + 1U + len + 1U + 1U;

    if (out == NULL ||
        len > MAX_DATA_LEN ||
        out_size < frame_len)
    {
        return 0;
    }

    size_t pos = 0;

    out[pos++] = SOF;
    out[pos++] = cmd;
    out[pos++] = len;

    for (uint8_t i = 0; i < len; ++i)
    {
        out[pos++] = data[i];
    }

    out[pos++] = checksum8_frame(cmd, len, data);
    out[pos++] = EOF_BYTE;

    return pos;
}
```

## 13. 推荐软件分层

```text
Application
   ↓
Command Handler
   ↓
Protocol
   ├─ Pack
   ├─ Parse
   ├─ CRC
   ├─ ACK
   └─ State Machine
   ↓
RingBuffer / Queue
   ↓
UART + DMA + IDLE
   ↓
Hardware
```

协议层只处理帧，不直接依赖具体 UART 实例或业务 GPIO。

## 14. 常见设计问题

| 问题 | 风险 | 处理方式 |
| --- | --- | --- |
| 无 LEN | 变长帧难解析 | 增加长度字段 |
| 只依赖帧尾 | 数据中出现相同字节时误判 | LEN 为主，EOF 为辅 |
| 结构体直接发送 | 对齐、填充、字节序不确定 | 显式序列化 |
| LEN 不做上限检查 | 缓冲区越界 | 解析 LEN 后立即校验 |
| CRC 覆盖范围不明确 | 两端结果不一致 | 协议文档固定范围 |
| 有 CRC 无 ACK | 无法确认执行结果 | 关键命令增加 ACK |
| 有重传无 SEQ | 命令可能重复执行 | 增加序号和去重 |
| 中断内执行业务 | 中断时间过长 | ISR 收数据，任务解析 |
| 无接收超时 | 残帧长期占用状态机 | 增加帧间超时 |
| 无版本字段 | 协议升级困难 | 预留 VER |

## 15. 选型建议

| 场景 | 推荐帧结构 |
| --- | --- |
| 简单点对点 | SOF + CMD + LEN + DATA + CHECK |
| 上位机调试 | 基础帧 + ACK + ERR |
| 多设备通信 | 增加 SRC / DST |
| 高可靠控制 | CRC16 + ACK + SEQ + 重传 |
| 长期维护产品 | 增加 VER + FLAGS |
| 高吞吐量 | DMA + RingBuffer + 状态机 |

协议设计的核心要求是：

```text
可解析
可校验
可恢复
可扩展
可维护
```
